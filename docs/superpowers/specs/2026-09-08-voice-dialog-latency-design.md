# 语音对话流畅度与首句延迟设计

## 目标

在不牺牲复杂问题完整回答的前提下，保持现有约 134 ms 的 LLM 首 token 性能，并将用户说完到助手开始播放首个自然短句的目标设为不超过 1 秒。该目标是端到端体验目标，不承诺复杂回答在 1 秒内全部生成完毕。

## 范围

本次只调整 Python 编排、TTS 队列、配置和自动化测试；不修改 RKNN3 推理运行时或引入新的第三方依赖。RKNN3 daemon 目前没有可调用的中途取消接口，因此生成中的模型推理不能在本次完全终止；编排层必须立即停止旧语音并隔离旧轮数据。

## 设计决策

### 1. 交互模式

默认启用可打断模式：播放期间仍处理 VAD、ASR partial 和完整语音段。`mute_mic_during_tts` 仅保留为排查声学回授的半双工开关，默认值改为 `false`。当该开关为 `true` 时，日志和状态事件明确表明打断已关闭。

打断只在 partial 已积累到 `barge_in.min_speech_sec` 且文本稳定时触发；完整的停止短语可以立即触发。停止意图仅匹配完整命令，不能把“停车”等普通问题误判为停止。

### 2. 流式首句

LLM worker 线程只负责读 socket 并把 token 安全投递到 asyncio 队列。主事件循环独占处理切句器、UI token 事件和 TTS 入队，避免跨线程同时调用 `feed()` 与 `finish()`。

首个满足自然停顿的短句立即进入 TTS，后续句子边生成边入队。UI token 事件按短时间窗口合并，避免每个 token 都触发 WebSocket 广播。首句长度维持 6 至 26 个字符，优先在标点或逗号处分割。

### 3. 轮次隔离与接力

每个用户语音段分配递增 `turn_id`。TTS 队列仅播放当前 `turn_id` 的文本和音频；打断时立即废弃旧轮尚未播放或正在合成的内容。即使旧 LLM 请求仍在后台收尾，其 token 也不得影响新一轮的切句器、状态、TTS 或历史。

用户说“停止”时清除接力缓存；用户说“继续”时只恢复最近一次被打断的未播内容。播放中的当前句不会作为“未播内容”保存，避免续播时重复已经听到的句首。

### 4. 服务可靠性

VAD 结束会向 turn worker 发送退出哨兵。`run()` 在退出时关闭 WebSocket server、停止 TTS worker，并让 ASR 资源释放。每一轮 ASR/LLM/TTS 异常只终止当前轮，发送错误事件并回到监听状态，不得杀死常驻服务。

turn queue 设置有限容量，并优先保留最新有效用户段；过期段被记录并丢弃，避免复杂回答期间积压旧问题。

### 5. 测试和度量

用标准库 `unittest` 覆盖：停止意图、续播清理、barge-in 最短时长、旧轮 TTS 隔离、turn worker 退出、单轮异常恢复和流式首句入队顺序。

每轮事件包含 VAD 结束、ASR 完成、LLM 首 token、TTS 首播四个单调时钟指标。日志输出端到端首播延迟和其分段，便于在 RK3588 板端判断 1 秒目标由 ASR、预填充还是 TTS 合成造成。

## 验收标准

- 配置默认可打断，播放期间说“停”或新问题会终止旧播放；半双工诊断模式显式关闭该能力。
- “停车场在哪里”不会被判为停止；“停”“停止”“别说了”会生效。
- 停止后说“继续”不会恢复旧回答；只有打断后“继续”会恢复尚未播放的部分。
- 旧轮 token、音频和异常不会影响新轮。
- `--inject-wav` 在语音处理和队列清空后退出。
- 测试在不依赖板端模型、麦克风或 WebSocket 客户端的情况下运行。
